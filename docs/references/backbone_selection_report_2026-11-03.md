# 基座选型简报：连通性感知 VLN

> **结论已修订：** 用户随后明确要求优先较新框架，并接受后期旗舰模型 API。本文 CA-Nav 首选建议已撤销，当前决策以根目录 plan.md 第2.4节为准。保留本文作为阶段评估和接口审计记录。

日期：2026-11-03。依据：项目 proposal、作者论文、官方仓库与模型卡。结论属于工程推荐，尚无本项目运行结果；4×4090 为用户报告，未连接核实。

## 1. 推荐结论

**第一版采用 CA-Nav 的地图式导航框架，指令解析适配本地 Qwen3-VL-8B-Instruct；保留原有 BLIP-2、GroundingDINO/RepViT-SAM 视觉组件，接入在线 RSSI belief 和加权路径规划。环境先选 Habitat + MP3D + R2R-CE。**

这里有两个不同的“基座”：CA-Nav 是完整导航系统；Qwen 是其中的语言/视觉语言模型。第一版 Qwen 只承担文本指令解析，不替换全部视觉模块，也不直接生成运动动作。保留视觉组件可以减少同时更换模块造成的归因困难。Qwen 的视觉能力留作后续扩展；其作为替代解析器的有效性仍须验证。[CA-Nav 官方仓库](https://github.com/Chenkehan21/CA-Nav-code)、[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct)

**推荐 8B 为首个固定配置，32B 为同框架的容量对照，不先上 122B。** 本项目的新增贡献是在线通信场估计与规划，模型不做新增导航训练或微调。换用 Qwen 后，应称为“基于 CA-Nav 的本地适配版”，不能将其结果直接当作原论文复现。

## 2. 候选对比

选择标准依次为：完整代码与任务入口、通信代价的接入难度、本地推理可行性、零样本边界、近期性能潜力。下表为定性工程判断，不是实测排名。

| 候选 | 已核查的能力与限制 | 本项目定位 |
|---|---|---|
| **CA-Nav** | 提供 R2R-CE 运行说明、显式价值地图、子目标和 FMM；原配置使用 GPT-4 解析及冻结视觉组件；Habitat 0.1.7 依赖较旧 | **首选开发框架**：与信号场和规划研究最匹配，先验证依赖与本地替换 |
| **Open-Nav** | 完整代码、开放 LLM 路线；官方运行脚本目前示例仍是 GPT-4o，不能以论文标题推断脚本默认免 API；依赖预训练 waypoint predictor/DD-PPO 编码器 | **工程备选/独立对照**；可不新增训练，但须披露既有导航训练组件 |
| **EmergeNav** | 论文报告 Qwen3-VL 8B/32B、不做任务训练；不依赖显式地图或 waypoint predictor；本轮未找到可确认的作者完整实现 | 新近本地零样本参考；暂不作为主工程依赖 |
| **SpaceVLN / AgenticNav** | 空间记忆/工具接口具有参考价值；SpaceVLN 项目页仍显示准备中，AgenticNav 项目页未提供本轮可核验的完整运行代码入口 | 跟踪、讨论和后续强对照，不把未核验的实现当成现成基座 |
| **LightNav-0** | 新近公开代码和 4B 导航权重，输出轨迹并提供远端服务；模型经过导航对齐训练，不是原始通用 VLM 的 training-free 方法 | 若后续接受冻结导航专用模型，可作强对照；当前地图代价接口需另建 |

来源：[CA-Nav 论文](https://arxiv.org/html/2412.10137v2)、[Open-Nav 仓库](https://github.com/YanyuanQiao/Open-Nav)、[官方默认运行脚本](https://github.com/YanyuanQiao/Open-Nav/blob/main/run_OpenNav.bash)、[EmergeNav 论文](https://arxiv.org/html/2603.16947v1)、[SpaceVLN 项目页](https://charles-donne.github.io/SpaceVLN/)、[AgenticNav 项目页](https://agenticnav-vln.github.io/)、[LightNav-0 官方仓库](https://github.com/lightorigins/LightNav-0)。未找到代码仅表示本轮检索结果，不能证明作者未发布。

## 3. 为什么仍选 CA-Nav，会不会太老？

CA-Nav 为 2024 年预印本、2025 年 TPAMI 工作，模型和环境依赖确实偏旧。选择它的依据是可改造的地图与规划链条，而非声称其代表 2026 年最高性能。我们的近期目标是证明：**同一冻结导航系统，加在线信号 belief 后，能否以可接受的导航损失降低断连。** 使用较成熟框架有助于隔离这项增益。[论文与版本信息](https://arxiv.org/abs/2412.10137)

代价是需要处理旧环境、组件较多，以及可能低于最新系统的导航成功率。因此 CA-Nav 可以支持第一阶段方法验证，不能单凭这一基座就认定论文实验充分。投稿前需在统一协议下增加一个较新的可运行基座或强对照；不能直接横比不同论文、模型和 episode 子集的 SR。

## 4. 具体技术栈与改造点

| 层级 | 第一版选择 | 改动范围 |
|---|---|---|
| 仿真与数据 | CA-Nav 原环境；MP3D + R2R-CE | 先一个场景/episode；不把 R2R 直接搬到未对齐 HM3D |
| 指令解析 | 本地 Qwen3-VL-8B-Instruct，冻结权重 | 输出原解析器所需 JSON；校验字段、子指令顺序与约束类型 |
| 视觉与任务进度 | 原 BLIP-2、GroundingDINO/RepViT-SAM、约束管理 | 第一版保持不变，固定模型版本 |
| 无线仿真 | 路径损耗 + 墙体衰减 + 阴影噪声 | 真值场只在仿真器/Oracle 中；在线模块仅见当前与历史 RSSI |
| 信号估计 | 时序贝叶斯更新 + 简单空间扩散基线 | 先保证未知区域、不确定性和时间更新定义清楚；GP 后续比较 |
| 规划 | 原目标选择链条 + 通信感知加权规划 | 先固定子目标检验绕行收益，再考虑通信感知子目标选择 |

**源码审计已经确认一个实质改造点：** `FMMPlanner.set_goal()` 对可通行掩码调用 `skfmm.distance`，目前求的是几何距离，不读取连续 RSSI 风险。因此不能只把信号图叠到可视化图上就声称接入路径代价。[官方规划器源码](https://github.com/Chenkehan21/CA-Nav-code/blob/8430359ff930880ccc74131d4c31d74a598a9b6e/vlnce_baselines/models/fmm_planner.py)

建议先在同一可通行栅格上实现 Dijkstra/A*，边代价使用 `距离 × (1 + λ × 连通风险)`，固定邻接与障碍处理。**λ=0 的同一规划器**作为严格消融基线，另保留原 FMM 结果，避免把换规划器的增益归到信号 belief。将来若改用变速 FMM，还要重新验证停止距离阈值：风险累计代价不再等于米制几何距离。

指令解析源码已有独立生成/缓存流程，可适配本地服务，但仍需更改模型、端点、路径和解析验证，不能承诺原仓库无需修改即可离线运行。首轮作者缓存只用于检查原环境；最终免第三方付费 API 的实验需用本地模型生成缓存并独立报告。[官方解析器源码](https://github.com/Chenkehan21/CA-Nav-code/blob/8430359ff930880ccc74131d4c31d74a598a9b6e/vlnce_baselines/common/instruction_tools.py)

## 5. 4×4090 如何使用

- 8B BF16 仅权重粗算约 16GB（十进制），不含缓存、视觉输入、推理框架与临时张量；短文本解析适合先尝试单卡，是否可与其他模块共卡以实测为准。
- 32B BF16 仅权重粗算约 64GB，需跨卡分片，叠加其他组件后不宜默认全部同时常驻。第一阶段没有必要用它占满四卡。
- **优先离线生成任务指令解析缓存，再释放 Qwen 显存运行视觉导航**；两阶段不要求所有组件同时装入。导航中若要实测远端视觉服务，则单独规划显存与请求循环。
- 上述是按参数量推算的容量判断，不是吞吐或显存实测。四张 24GB 卡不是单张 96GB 卡；服务器 PCIe 拓扑、可用显存及旧 Habitat 与现代模型环境兼容性均待核实。建议两个独立环境/服务，避免强行合并依赖。

模型及推理接口依据：[8B 官方模型卡](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct)、[32B 官方模型卡](https://huggingface.co/Qwen/Qwen3-VL-32B-Instruct)。部署到自有服务器后不产生第三方逐 token 费用，但仍有服务器、电力和时间成本。

## 6. 先验收什么，何时更换基座

1. **原环境可跑：** 锁定仓库提交 `8430359ff930880ccc74131d4c31d74a598a9b6e`，检查数据/权重下载和代码许可；完成一个作者缓存驱动的 NoSignal episode。仓库树本轮未见独立 LICENSE 文件，复用许可待确认。
2. **本地解析可用：** 固定小批指令，检查 JSON 合法性及语义，再在同一 episode 集比较缓存解析与 Qwen 解析的 NoSignal 导航指标。不能仅凭 JSON 正确认定导航等价。
3. **Oracle 有收益：** 先做可绕行的双路径场景，再用多个场景/AP 布局比较同一加权规划器的 λ=0 与 StaticMap；同时报告 SR/SPL/nDTW、断连与绕行。几何导航若无路径选择余地，应先检查场景设计。
4. **Online Belief 有增益：** 固定上述基座、episode 和预算，再比较 Reactive 与在线估计；测试场景参数不参与调参。

若旧环境/权重不可获得、许可无法确认或本地替换明显破坏导航，切换 Open-Nav 作为工程备选，并重新评估路径代价接口。若 Oracle 在合理导航代价下没有通信收益，应先检查任务与可选路径，而不是直接增大模型或加入训练。

**应用叙事边界：** CA-Nav 解析低频且可以缓存，中途失联并不必然中断推理。第一阶段主张是“改善连接质量”，不能直接写成“避免云推理失败”。若要保留后者，需要把持续视觉推理放到自有远端服务器，明确 WiFi 请求时序、超时及安全回退，并补充服务测量。这可以免付费第三方 API，但属于后续系统实验。
